# AppleBridge — Project Guide for Claude

## What this is
**AppleBridge connects Claude Code to a real Mac System 7.6.1 running in Basilisk II**, so an AI can build, compile, link, and run authentic 68k Macintosh software via natural language. The bridge carries MPW/ToolServer commands to the emulated Mac and returns their output.

## What we want to achieve
A **reliable, self-healing development bridge** that lets Claude drive the classic Mac like a normal toolchain:
- Write C / 68k assembly on the host → compile (SC/Asm) → link → run on System 7.6.1.
- Get **real command output back** (errors, listings, file dumps) for closed-loop debugging.
- Expose it all as **MCP tools** so any Claude session can use it without glue code.
- Survive the rough edges of a 1990s emulator (dropped connections, flow control, AE quirks) **without manual restarts**.

The north star: *talking to a 30-year-old Mac should feel as dependable as a local shell.*

## Architecture (NAT-reversed)
```
Claude ⇄ MCP server (stdio)  ──:9001──▶  host_server.py  ◀──:9000──  Mac daemon (AppleBridge)  ──Apple Events──▶  ToolServer / MPW
```
The **Mac daemon connects OUT** to the host (the emulator sits behind NAT, so the host can't dial in). `host_server.py` serves **:9000** (daemon) + **:9001** (control/MCP). Wire protocol: request `COMMAND:<len>\n<payload>`; response `STATUS:<code>\rSTDOUT:<len>\r<data>\rSTDERR:<len>\r<data>\r\r` (read **by declared length**, not by terminator).

## Start the stack
**One-shot:** `cd host && ./start_stack.sh` — aliases `.154` onto the default-route interface (the freeze-avoidance rule below), (re)starts the host server, and launches Basilisk II. Then do the two in-emulator steps (daemon + ToolServer) it prints. Manual steps:
1. **Host server**: `cd host && nohup ./run_server.sh & ` — uses **`/usr/bin/python3`**, never the venv (macOS firewall blocks the un-allowlisted venv binary). Log: `/tmp/applebridge_server.log`. **Order vs. the emulator does not matter** (PR #75): a daemon that starts first just retries and connects within ~40 s, and the control port answers throughout. The old "server first or the daemon fouls the socket" rule was a blocking `accept()` bug, not a socket problem.
2. **Mac daemon (faceless, v0.6.0)**: with autostart installed it launches **automatically on boot** — no window — and **chain-launches** its helper apps (ToolServer first) from the prefs file. Otherwise launch `:bin:AppleBridge` by hand. Only **ToolServer ('MPSX')** returns command output (MPW Shell gives empty AE replies). Configure the host IP, the helper list, and autostart via **AppleBridgeConfig** (`:bin:AppleBridgeConfig`) — see `mac/config/README.md`.
3. **MCP server**: registered in `.mcp.json` as `applebridge`. **20 tools** (grew from the original 7 in 2026-06-29's MCP push):
   - *Surface A — drive a build, read output:* `mpw_execute`, `mac_compile`, `mac_read_file`, `mac_list_files` (column-parsed, handles spaces), `mac_build` (one-shot SC→Link→Rez→SetFile, verified by artifact), `mac_send_apple_event` (arbitrary AE to any scriptable app).
   - *Surface B — move bytes, run, observe, interact:* `mac_put_file` / `mac_get_file` (fork-aware binary, MacBinary), `mac_write_file` (text), `launch_app`, `mac_screenshot` (optional region crop), `mac_type` / `mac_key` / `mac_click` (synthetic input into the front app), `mac_clipboard_get` / `mac_clipboard_set` (guest TEXT scrap ↔ host pasteboard).
   - *Network discovery:* `mac_appletalk_browse` (NBP name lookup in the daemon — the Chooser's list of `AFPServer`/`LaserWriter`/`Workstation` entities, headless: no ToolServer, no GUI driving; ~3 s for NBP's retry window; AppleTalk being off is reported as an error, not as an empty list).
   - *Lifecycle / liveness:* `mac_status` (daemon/ToolServer/heartbeat; answers even when the daemon is down), **`bridge_doctor`** (cross-layer diagnosis: launchd job, :9000/:9001 listeners, `.154` alias placement vs. default route, BasiliskII + `etherhelpertool`, emulator `ether` backend, observed guest peer IP — runs host-side in the MCP process, so it answers even when the host server is down), `mac_reboot` (in-process `ShutDwnStart`), `mac_restart_toolserver`, `run_applescript` (host-side `osascript`).
   - New tools register on the next MCP-server restart (the running server caches the tool list).

Smoke test: `cd host && /usr/bin/python3 send_command.py 'Echo HELLO'`.

## Hard rules (learned the hard way)
- **`Link -model far` is the default linker** — verified and leaner output. `ILink` is *not* broken: with the correct `{CLibraries}`/`{Libraries}` paths it links, runs, and round-trips commands cleanly (verified 2026-06-26). The old "ILink crashes Basilisk II" belief was a misdiagnosis — the committed `BuildIt` used an empty `{LIBS}`, so its lib paths resolved to nothing → a broken binary that crashed *on launch*. ILink is fine to use; it just yields a slightly larger binary plus a big `.NJ` incremental file, so `Link` stays the default.
- **`/usr/bin/python3` for the host server** (firewall). Stdlib-only, so system Python suffices.
- **Re-run `Rez AppleBridge_res.r` after every link** — the `SIZE` resource (`isHighLevelEventAware`) is required or every command fails with `-903`.
- **Never `2>&1`** in MPW (crashes the shell) — use `≥ file.err` to capture stderr.
- **Build off the running daemon**: link to `:bin:AppleBridge.new`, then swap; a heavy link in the same ToolServer that serves the bridge can take it (and the AE layer) down.
- **Encoding**: host UTF-8/LF ↔ Mac MacRoman/CR — use `host/encoding_convert.py`.
- Long commands (e.g. `Link`) may return `-1712` (AE timeout) **yet still complete** — verify by the artifact, not the status.
- **Host `.154` must live on the default-route interface** (where the guest's MACNAT exits — normally Wi-Fi `en0`), *not* a second NIC. If it's on the wrong interface, the daemon hangs on "CONNECTING" and freezes the emulator at 100% CPU (synchronous `OTConnect` starving the cooperative scheduler). `host/start_stack.sh` sets this up. **Never pre-create a bridge** — `etherhelpertool` owns `en8` directly; a manual `bridge100` SIGSEGVs it (`fret == -10`). The guest is behind MACNAT, so it is **never pingable** — diagnose via the *outbound* connection, not ICMP. See `TROUBLESHOOTING.md` → "Daemon hangs on CONNECTING".

## Status (2026-07-05)
AppleBridge runs as a **System 7 background service** with an optional on-screen monitor. The daemon speaks **wire protocol v0.2** (version negotiation + optional mutual auth); the host server auto-starts via launchd. Current daemon **0.8d25**; the MCP surface is **27 tools** (counted from `mcp/tools.py`). Validated live on **both** Basilisk II (System 7.6.1) and SheepShaver (PowerPC / Mac OS 9).
**ClaudeApp demo — an animated GIF in a System 7 About box (2026-07-05, `mac/claudeapp/`).** A windowed Toolbox app authored, compiled (in the **THINK C** IDE, driven over the bridge with host `cliclick` + injected keys), and run entirely across AppleBridge; its About box plays a real 16-frame animation. Host tool **`host/tools/gif_to_rez.py`** turns a GIF into classic-Mac resources: coalesce → scale 320×120 → one shared 25-colour `'clut'` → PackBits per row (602 KB → **89 KB**, round-trip-verified) → `'clut'`/`'GFin'`/`'Gfrm'` (self-contained `about_inline.r`, merged with `Rez -a`). The guest blits from a hand-built off-screen 8-bit `PixMap` via `CopyBits` on a **`WaitNextEvent`** tick — the yield is mandatory: a `Button()` spin starves the background daemon and freezes the bridge. Deployed to **OS 9** too by extracting the 68K app from Basilisk's (powered-off) disk image with `hfsutils` and `mac_put_file`-ing it across — runs under OS 9's emulator, animation intact. Two CMS write-ups: the [build story](https://pit.390er.de/applebridge/animated-about-box-gif-think-c/) and the [components overview](https://pit.390er.de/applebridge/applebridge-components-c-and-assembly/). See [[applebridge-claudeapp-animated-about-gif]].

**Journaling driver — hands-off menu & modal-dialog driving (2026-07-04→05, branch `docs/journaling-drvr-mechanics`; daemon 0.8d11–d20).** A native 68K journaling **`DRVR`** (`mac/journal/ABJournal.a`) lets the faceless daemon drive the classic tracking loops that synthetic `PostEvent`/click injection can't reach (`MenuSelect`/`PopUpMenuSelect`/`ModalDialog` poll the hardware mouse). Shipped in steps, each verified live over the bridge: the step-3 ROM gate (journaling is consulted on this ROM), **faceless-daemon install** (`JGATE`), **popup menu-driving** (`JMENU`, d14), **real menu-bar** driving (`JABOUT` opened the About box with zero synthetic input, d15), an **interrupt-time freeze watchdog** (`JSAFE`, d18 — a Time Manager task zeroes `JournalFlag` at interrupt time, recovering a modal that spins at 100 % without polling the journal), and **modal Standard File button-driving** (`JSF`, d16→**d20**). The `JSF` capstone (d20) resolves the last blocker: a background daemon's `SFGetFile` gets no events (they route to the front Finder) so its `ModalDialog` is undismissable — because `SetFrontProcess(self)` is *asynchronous* and `ModalDialog` never yields to let the switch land (d19 tried it and hard-froze). d20 **pumps `WaitNextEvent` until `GetFrontProcess` confirms the daemon is truly front** before opening the modal, and **bails before the modal if the switch never lands** (a failed foreground can't peg the CPU). Verified: `JSF:200:3`→Cancel dismissed, `JSF:200:1`→Open selected `AB.old4`, CPU 6–11 % throughout, no freeze. The **by-name menu verb** `MENU:<title>:<item>` (d22, hardened d23) generalises `JABOUT` to any title+item by name on the daemon's **own** menu bar (walks the live menu list → `menuLeft`; matches item text → index; journal-drives `MenuSelect` → dispatches). A feasibility spike (**`JPROBE`**, d21) proved that reaching an **arbitrary front app** is a dead end for journaling — `MenuSelect` uses the caller's menu list, and a background `WaitNextEvent` never pumps the journal — so foreign-app shortcut-less menus stay host-`cliclick`-only (local Basilisk). Design + full progress: `docs/JOURNALING_MENU_BY_NAME.md`, [[applebridge-journaling-driver-feasibility]].

**Live transport hot-swap + active-transport monitor label (2026-07-04, PR #66; daemon 0.8d9–d10).** Two related changes on the transport seam. **(1) Hot-swap:** the daemon re-reads the `NET=` pref at the top of its main loop (throttled to ~5 s) and, on a change, tears down the active OT/MacTCP/Serial stack and brings up the new one **live** — dropping the link so the reconnect loop re-dials on the new backend, **no relaunch**. Only the transport-selecting fields are adopted from the re-read (IP/token/apps/home stay as loaded); the poll runs only *between* commands. A Control-Panel radio flip (or a `NET=` edit over the bridge) switches stacks in ~4 s — verified both directions on Basilisk II with continuous uptime and a ToolServer `Echo` round-tripping over the live-swapped MacTCP stack. **(2) Monitor label:** since the stack can now change at runtime, the Verbose console **footer** leads with a labelled `NET OT` / `NET MacTCP` / `NET Serial` field; it reads `ABActiveTransport()` on every refresh, so a hot-swap relabels it within seconds. A shared **`ABTransportName()`** helper (`transport.c`/`.h`) backs both the footer and STAT's `net=` — which also **fixes STAT**, previously mislabelling `Serial` as `OT`. Verified live end-to-end: built, self-updated over the bridge, rebooted onto the new binary — footer `NET OT`, on-device `vers` **0.8d10**, STAT `net=OT`. (Intervening releases since d4: d5 clean power-off — `SHUTDOWN` + `mac_shutdown`, [[applebridge-never-kill-basilisk]]; d6 monitor telemetry footer — err/latency health bar; d7–d8 synthetic-input completeness + host-side crash black-box.)

**Input modifiers, `mac_menu`, and daemon self-update (2026-07-02, PRs #56–#58; daemon 0.8d4).** Two capabilities on top of v0.2. **(1) Key modifiers + menus:** the `KEY:` verb now carries an Event Manager modifier mask, `mac_key` gained a `modifiers` list, and a new **`mac_menu`** injects a menu command's Command-key equivalent. The daemon stamps `evtQModifiers` via `PPostEvent` **and** holds the low-memory `KeyMap` bits (belt-and-suspenders), so Cmd-key shortcuts drive the front app's `MenuKey` — a synthetic click can't, because `MenuSelect` is a modal tracking loop the background daemon isn't scheduled during. Verified on Basilisk + SheepShaver (Cmd-A/Cmd-Q in SimpleText). Menu-by-name for shortcut-less items stays deferred (needs a journaling hook). See `docs/INPUT_MODIFIERS_AND_MENUS.md`, [[applebridge-input-modifiers-menu]]. **(2) Bridge-drivable self-update:** a **`SWAPSELF`** verb + **`mac_update_daemon`** tool. The installer can't hot-update a running daemon (it *copies* → `fBsyErr` on the open file), but *renaming* an open file is allowed — it edits the catalog, not the open forks — so the daemon renames **itself** aside (`FSpRename` via its own `processAppSpec`) and the host-staged `<name> new` into place; a reboot lets the watchdog launch the new binary. `STAT` now reports `home=`. Verified on-device on **both** System 7 and Mac OS 9 (`FSpRename` of a running app works on OS 9 too), both directions, the OS-9 second update fully hands-off — so the manual Shift-boot/Finder swap for updates is gone (the only manual step left is placing the *first* `SWAPSELF`-capable daemon on a fresh machine). See `docs/SELF_UPDATE.md`, [[applebridge-daemon-self-update]].

**Wire protocol v0.2 (2026-07-02, PRs #48 / #51 / #50).** The bridge gained **version negotiation** and **opt-in mutual authentication**. On connect the host sends a `HELLO:` probe; a v0.1 daemon answers "Invalid command format" and the host falls back to legacy, so host and daemon upgrade independently. When a token is set on both sides (guest prefs `TOKEN=` + host `APPLEBRIDGE_TOKEN`) the two run a **fail-closed** FNV-1a-64 challenge/response — the digest is computed identically on the 68K daemon (32-bit halves, since MPW C has no 64-bit int) and the host, verified live (`negotiated protocol v2 + auth OK`). Also host-side bounded reads (`MAX_DECLARED` / `MAX_CTRL_REQUEST`). The default (no token) is unchanged. Design + migration in `docs/PROTOCOL_v0.2.md`; persistent connections were consciously deferred. See [[applebridge-protocol-v0.2-progress]].

**MCP tooling build-out (2026-06-29).** The MCP surface grew **7 → 20 tools** — the whole "[tooling-gaps](https://pit.390er.de/applebridge/applebridge-mcp-tooling-gaps-deploy-and-run/)" roadmap shipped + merged: fork-aware binary transfer (`mac_put_file`/`mac_get_file`, proven by deploying a host-built **Retro68** APPL and launching it), synthetic input injection (`mac_type`/`mac_key`/`mac_click`), `mac_status` liveness, one-shot `mac_build`, quality fixes, plus the extras `mac_send_apple_event` and clipboard get/set. A working **`mac_reboot`** (Shutdown Manager `ShutDwnStart`, not the Finder-AE stub) makes build→deploy→activate hands-off (PRs #32–#38).

**Verbose monitor window (2026-06-29, PR #39).** The daemon now opens an on-screen **Verbose** log window (it is `backgroundAndForeground` + `getFrontClicks` in the SIZE resource — clickable; NOT `onlyBackground`). It shows full command output, bold command lines, and a working vertical scrollbar. *Gotcha bank* in [[applebridge-verbose-console-ux]]: a styled `TERec` reports `lineHeight = -1` (broke scroll-range math); the scrollbar is hit-tested geometrically because `FindControl`/`TrackControl` don't engage for this window; injected clicks can't reach the daemon's own window (test interactively).

**Faceless-service arc (PRs #21–#23), verified live by a cold reboot.** The daemon (then `onlyBackground`; **since 2026-06-29 it is `backgroundAndForeground` + `getFrontClicks`** with the clickable Verbose monitor window above) reads its config from an **AppleBridge Prefs** text file, **chain-launches** its helpers (ToolServer first) on startup, and installs itself into the System Folder's **Startup Items** as a self-made Finder alias — so a cold boot brings the bridge up invisibly and automatically, ToolServer and all, ready for `Echo HELLO` → `STATUS:0` with zero manual launching. Three components + one shared file:
- **AppleBridge** — the faceless daemon (`onlyBackground`, creator `'ABrg'`): OT transport + AE-client to ToolServer + chain-launch. Quits cleanly via `kAEQuitApplication` and the `QUITDAEMON` wire verb.
- **AppleBridgeConfig** — foreground control panel (creator `'ABcf'`): shows daemon up/down + autostart state, picks helper apps (Standard File → `APP=`), and installs/removes autostart (alias in Startup Items). **No Launch/Stop Daemon buttons** — quitting the faceless daemon tears down Open Transport and trips a Sequoia/SDL2 host crash, and the daemon is meant to run continuously anyway. See `mac/config/README.md`.
- **AppleBridge Prefs** — flat `IP=`/`DEBUG=`/`APP=` text in the Preferences folder, shared by daemon + config app. (Gotcha: an `APP=` entry that opens a fullscreen presentation — e.g. *About Mac OS 7.6.1 Update* — freezes the emulator at chain-launch; keep the list to real helper apps like ToolServer.)

**Prior hardening (v0.5.x, still in force).** Async `OTConnect` + application-level heartbeat (no host-down freeze; PRs #10–#13); v0.5.7 audit hardening (PR #19): length-framed *receive* reassembly, teardown-on-send-failure, an off-stack 64 KB buffer, a longer build AE timeout (no spurious `-1712`), watchdog reconnect backoff. Host side: length-framed reads, `kOTFlowErr` handling, **>64 KB** heap-streamed responses; the MCP false-success fix (PR #17); repo cleanup of pre-NAT + Swift code (PR #18). Screenshots stream the emulated screen → PNG host-side. The old "GUI apps crash BAII" was a **broken guest binary**, not a window bug (PR #15) — build GUI apps in **C** (`MinQDC`), assembly for **MPW tools** (`MinAsm`).

**Roadmap status** (see the [ledger](https://pit.390er.de/applebridge/applebridge-roadmap-ledger-progress-and-status-tracker/)). Phases 1–4 are done: the transport go/no-go was decided (**slirp is no-go** — ~−80 % bulk throughput on this build's legacy slirp; stay on `etherhelper/en8`, PR-benchmarked in `host/bench_transport.py`), protocol **v0.2** shipped (above), host-edge tests + CI landed (PRs #46–#47), and the docs hygiene pass merged (PR #52). **Phase 5 is now essentially cleared** — everything tractable in-emulator has shipped: the **native PowerPC build** (MrC + PPCLink on OS 9, [[applebridge-native-ppc-compile-os9]]), the **control-port token guard** (PR #62), the **e2e-smoke** test tier (PR #60), **ToolServer on OS 9** ([[applebridge-toolserver-on-os9]]), the **Control-Panel (cdev)** port + polish (PR #63 — daemon/autostart status LEDs, host-IP line, helper list with Add/Remove/select, Standard File picker, `NET=` transport radio), the **monitor telemetry footer** (d6) and the `NET`-transport label (d10, PR #66), **clean power-off** (d5, [[applebridge-never-kill-basilisk]]), **synthetic-input completeness + crash black-box** (d8), input modifiers + `mac_menu` (PR #56), and bridge-drivable daemon self-update (PR #58). SheepShaver/PowerPC is **validated live** (protocol v2, screenshot, a FoxPro session, `mac_menu`, `SWAPSELF`); the daemon-relaunch **watchdog** ships (PR #25). **What remains is hardware-gated or a deferred deep-dive, not routine work:** the **serial** live round-trip on *real hardware* (needs a physical 68k Mac + cable; the backend + drag-install package already merged, PRs #53/#54); the **journaling driver** (68k `DRVR`) is now built on branch `docs/journaling-drvr-mechanics` (daemon 0.8d23) — popup + real menu-bar driving, an interrupt-time freeze watchdog, **modal-dialog mouse via `JSF`**, and **by-name menu driving via `MENU:<title>:<item>`** (own menu bar, hardened) all work live; a `JPROBE` spike proved cross-process **front-app** menu driving is a dead end for journaling (foreign shortcut-less menus stay host-`cliclick`-only, local Basilisk). Optional leftovers: a `mac_menu(byName=…)` MCP wrapper ([[applebridge-journaling-driver-feasibility]]); the presence **INIT** (needs 68k asm, not C); and **persistent connections** (consciously deferred in v0.2). Future ideas also in `README.md` / `ARCHITECTURE.md`.

## Driving the guest's real mouse (local emulator only)
Menus, Standard File lists and other **modal tracking loops poll the hardware pointer**, so synthetic `mac_click` never reaches them. Use **`host/guest_input.py`**, which takes **guest** coordinates (what a screenshot shows) and handles the host mapping itself:

```bash
host/guest_input.py geometry                     # origin, title bar, live mapping
host/guest_input.py click 300 472                # click the desktop -> Finder frontmost
host/guest_input.py menu 18 9 70 112             # Apple menu -> Chooser, ONE gesture
host/guest_input.py shot out.png --region 250,80,560,420
```

It exists because each of these bit once: it **refuses** to click when the emulator is not frontmost (a stray click landed in the host's browser), it re-reads the window origin **before every gesture** (the window moved 448,128 → 605,104 mid-session), it keeps a menu's press→drag→release in a **single** `cliclick` call (a menu held open across two screenshots starved the daemon into `OTSnd err=-3158` + a 30 s reconnect), and `shot` captures **host-side** because the daemon cannot answer while a tracking loop owns the machine. Out-of-guest coordinates are refused outright. An MCP wrapper is deliberately **not** decided yet.
